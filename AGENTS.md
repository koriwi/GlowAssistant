# Collaboration preferences

- Keep responses short, information-dense, and easy to scan. No walls of text.
- The user wants close control over scope and decisions. Do only the work explicitly requested; do not start unsolicited coding, refactors, or features.
- For broad or ambiguous requests, briefly outline the proposed scope and clarify consequential choices before implementing. Resolve routine details within agreed scope without repeated approval requests.
- Prefer simple, readable solutions. Avoid premature optimization, speculative abstractions, and unnecessary dependencies.
- Add comments only when the reason or behavior would otherwise be unclear. Keep them short; fragments are fine. Do not narrate obvious code.

# Repository

- HACS integration: `custom_components/glow_assistant`, domain `glow_assistant`, targeting the user's HA 2026.4.2. `hacs.json` is at the repository root. Repository URL: https://github.com/koriwi/GlowAssistant. Keep the HA minimum and test dependency aligned with this version; check with the user before raising it.
- HA 2026.4.2 uses `voluptuous` config schemas; do not use newer `probatio` or `vol.Secret` APIs. API-key fields use password text selectors.
- HA config/options UI has three expanded model sections (decider, smart-home answer, general), with prompts, connections, numeric settings and request limits kept in the relevant model section. General has an enable checkbox; disabled general requests use the fixed unsure reply. Prompt text is not templated; blank restores the default.
- Integration reads HA registry/state snapshots, never HA MCP or a long-lived HA token. It uses HA's exposed-entity settings minus optional exclusions. Action requests currently run service → target_scope → area/target resolution → parameter detection → stop. target_scope classifies entities (specific arealess/room-independent targets), entities_implied_area (one speaker area), entities_explicit_area (one explicit area), areas (one or more explicit areas without specific entities), implied_area (speaker area without specific entities), or unsure; value extraction and execution remain paused. For areas, one action_areas Choice selects every area above action_area_probability_threshold; these areas are final targets, without entity selection. For implied_area, use the supplied speaker area directly with no area/entity model calls. For entities_explicit_area, action_areas uses the unique highest probability (not the multi-area threshold), then filters candidates by domain and that area. For entities_implied_area, use speaker context to filter by domain and area without another area model call. For arealess entities, filter only by domain, including assigned/unassigned entities. The three entity paths use one action_entities Choice and retain every entity above action_entity_probability_threshold. Both probability thresholds default to 0.15 and have independent benchmark flags --action-area-threshold / --action-entity-threshold. none never overrides retained real options in multi-selection; ties or highest none in single-area selection stop. Empty selections and area/domain mismatches never broaden the search. Return the selected action's complete HA metadata under action_metadata and in the native service trace result; retain it with benchmark.py --json and native debug cards, and log it at DEBUG in conversation.py. Default benchmark output is compact and shows the action, speaker room, target type, area filter, candidate counts, targets, confidence and timings. Full option probabilities remain available in native debug cards and --json. No value extraction, device execution or answer-model call runs. After successful target resolution, optional parameter detection runs with the resolved target included and uses one Choice question over optional fields plus none, flattening nested UI groups. Required fields remain separate. Keep each actual field strictly above parameter_probability_threshold (default 0.15); ignore overall confidence and never let none override retained parameters. No optional fields means no extra call. Required fields are listed automatically without a model choice. Default console output shows retained optional probabilities plus none; --json retains dropped probabilities too. Prompt and probability threshold are under Decider; benchmark.py has --parameter-threshold, independent of --confidence. For target_scope, supply optional speaker_area to AgentEngine.process. HA resolves it from user_input.device_id and its device area; benchmark.py uses --speaker-area. Offer entities_implied_area and implied_area only when a speaker area is supplied; never invent a location. Specific entity targets with an area restriction support one area only; multiple explicit areas mean unsure. Arealess means room-independent, not a missing HA area assignment or an omitted room name; a unique device name alone is insufficient. Room-independent logical targets do not inherit speaker-area restrictions automatically; local roles such as desk/ceiling lamps can. The saved stock scope prompt upgrades automatically; custom prompts remain. History and pipeline language reach this call. No entity catalog is needed. Keep the existing supported action choices; broader action discovery is a separate change. Legacy numeric/text helpers and their settings remain available but are not used by the action branch.
- Every state query selects an area (specific room or all_areas), then one reporting domain. Queries without an identified room use all_areas, including exposed entities without room assignments. No no_area choice is offered for queries. Domain selection receives the request, selected area and domain choices, without an entity catalog. Unsure or low-confidence choices stop without restoring all domains. The old domain-filter confidence migrates to domain_confidence; legacy domain keep/drop prompts and uncertainty switch are unused.
- After area/domain selection, query_type selects yes_no or complex. Yes/no queries use one binary_answer decision over filtered candidate states (yes/no/unsure), skip entity keep/drop, and send only state_answer to the answer model for translation into the Assist language. Complex queries keep entity filtering. Both prompts and thresholds are under Decider and in native debug cards. Unsure stops with the configured reply.
- Query target keep/drop includes each candidate's current state without full attributes. Questions name entity IDs and states directly, without positional lookups. Respect explicit state conditions, retaining relevant unknown/unavailable entities to report uncertainty. Above target_filter_confidence follow keep/drop; at or below it follow query_target_keep_uncertain, default false. Empty or invalid selections stop. The saved stock target prompt upgrades automatically; custom prompts are preserved.
- Assist debugging uses native `ChatLog` external `ToolInput` calls and `ToolResultContent` entries (`chat_log_trace.py`), visible in the upper conversation area. Engine trace callbacks report stage choices, confidence/thresholds, timing, usage and failures without extra model/device calls. The user explicitly requested the smart-home answer's complete input: include exact messages after adding prompt, pipeline language and history, plus model/settings. Keep credentials and headers out of all traces, and keep decider task instructions out of trace metadata. No frontend changes.
- Pure integration engine/client/settings tests run offline. `test_ha_integration.py` needs HA (Python 3.14.2+, `requirements-ha-test.txt`) and otherwise skips explicitly. GitHub Actions runs HA tests and hassfest. Do not claim those checks ran locally if HA could not be installed.
- The integration is self-contained; its numeric helper is an isolated copy of the prototype helper. Keep probe/debugging behavior out of the HA path.
- `benchmark.py` imports the integration's `AgentEngine` and `ModelClient` directly; do not copy decision logic into the CLI. It uses `.env` model connections and optional confidence overrides. An authenticated admin-only `GET /api/glow_assistant/snapshot` returns the same exposed/excluded snapshot plus settings with API keys and MCP tokens removed. `HA_URL`, `HA_TOKEN` and optional `GLOW_ENTRY_ID` configure access. Benchmarks use `dry_run=True`: actions stop after target resolution and parameter detection, retaining metadata, state queries run normally, and general MCP execution is blocked. - The currently unused integration free-text helper is limited to `todo.add_item.item`, `notify.send_message.message`, and `assist_satellite.announce.message`. One decider request classifies each word as keep/drop; default behavior keeps only confidence strictly above `text_confidence` (default 0.5), then joins in original order. The optional text uncertainty switch can retain low-confidence words. Match the working probe: instructions once in `state.task`, short word questions, and item-specific criteria. Item and message prompts and the threshold live under Decider. Keep task instructions out of debug records. Empty or invalid selections must not execute. Keep `text_probe.py` independent; no string casting or additional text actions.

No extra expiry, target-reuse mechanism, extra decider call, tool-result history or reasoning history. Use fresh HA state values for numeric execution. History is scoped to the current Assist conversation and defaults to disabled.
- Local Python 3.11+ prototype; eventual goal is a Home Assistant conversation agent integration.
- Install dependencies: `python -m pip install -r requirements.txt` in a virtual environment.
- Inspect built-in HA MCP: `python prototype.py --inspect`.
- Classify a prompt: `python prototype.py "your request"`.
- Classification fetches MCP tools/context once per run, then selects service/domain → area → compatible target. No disk cache.
- Area selection receives only prompt and area names/aliases. `no_area` retains all domain candidates; `unsure` stops target selection. Known areas filter target candidates by domain and canonical area name.
- Service/domain selection receives the user prompt, tool definitions and domain choices, without the entity catalog. Target and numeric stages use the cached entity data.
- Unqualified warmer/colder requests mean heating/AC (`climate`). Light color temperature requires an explicit lighting reference.
- Non-query commands execute target-only MCP tools and supported temperature/brightness setters automatically. Other extra values and ambiguous/unsupported targets are skipped. Never run live device actions as an incidental test.
- Numeric setters use a fourth decider request with Score. Temperature constants: 16–26 °C, 9 levels. Relative temperature changes use the existing thermostat target (`temperature`), not the measured `current_temperature`.
- Temperature execution currently uses `TEMPERATURE_STEP = 1.0`, matching the user's reported thermostat step. Send whole-degree integers and preserve the direction of subdegree relative changes; the isolated probe keeps raw estimates.
- Shared numeric request/decoding logic lives in `numeric_values.py`. The standalone probe remains available for isolated experiments.
- State questions can select `query_state`, using cached states/attributes with no service. Domain and target selection still run; `unsure` remains separate.
- State-query output displays cached values/attributes; area queries list matching entities in the selected domain. JSON includes `state_info`.
- Default output is a short summary including the area filter; `--json` includes all stages' scores, alternatives, usage and timings.
- Optional `tts_answer.py` generates spoken text after state lookup/execution via independent `ANSWER_URL`, `ANSWER_MODEL`, `ANSWER_API_KEY` chat-completions settings. Blank URL/model disables it. Send only final selections and selected state/execution facts, not the entity/tool catalog or classifier scores. Answer failures preserve the execution outcome and never retry the action.
- In the local prototype, selection fallback `unsure` returns exactly `ich bin mir nicht sicher` without a chat-model call. Only the first service question also offers `not-smarthome-related`, routing the original request directly to the smart chat model via independent `GENERAL_URL`, `GENERAL_MODEL`, `GENERAL_API_KEY`. Later unresolved choices and skipped operations stay `unsure`. Prototype general replies have no MCP/tools and bypass the small answer model.
- Run offline checks: `python -m unittest -v`.
