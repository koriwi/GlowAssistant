# Collaboration preferences

- Keep responses short, information-dense, and easy to scan. No walls of text.
- The user wants close control over scope and decisions. Do only the work explicitly requested; do not start unsolicited coding, refactors, or features.
- For broad or ambiguous requests, briefly outline the proposed scope and clarify consequential choices before implementing. Resolve routine details within agreed scope without repeated approval requests.
- Prefer simple, readable solutions. Avoid premature optimization, speculative abstractions, and unnecessary dependencies.
- Add comments only when the reason or behavior would otherwise be unclear. Keep them short; fragments are fine. Do not narrate obvious code.

- All multi-select Choice selectors normalize the configured threshold with probability_cutoff in validation.py: effective cutoff = configured threshold / max(1, real option count). Exclude none/unsure first. Two real options halve the configured cutoff; three divide it by three. Apply this to action areas/entities, query targets, optional parameters and text words, with inclusive p >= effective cutoff. At threshold 1, uniformly distributed real options survive; threshold 0 retains zero-probability real options too. Defaults and flag names remain unchanged. Single-choice confidence and unique-highest area selection do not normalize. Debug includes probability_threshold (configured), real_option_count and effective_probability_threshold; CLI prints the calculation and effective drop reason. Keep the concern comment at the shared calculation: extra irrelevant options lower the cutoff too and can admit weak matches.
